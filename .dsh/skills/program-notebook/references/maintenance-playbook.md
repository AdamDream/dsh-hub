# Program Notebook 维护手册

只在进行结构性改动、判断文档同步范围或验证最终状态时读取本文件。

## 证据规则

**不推测。** 写入任何架构事实、缺陷、限制或风险前，必须通过以下至少一种证据验证：

- 当前源码和配置
- 搜索结果和调用点
- 测试文件与执行结果
- Git diff、status 或历史
- 已读且仍与实现一致的项目文档

工具报告只是证据入口，不能替代读取源码。无法验证的内容明确标记为“未验证”，不要补全猜测。

## 结构性变化判定

以下变化必须检查 notebook 和相关专题文档：

- 新增、删除或移动模块、入口点、公共 API
- 生命周期、任务/线程所有权、并发边界变化
- 函数、服务、进程、设备之间的数据流变化
- 状态机、运行模式、错误处理、安全门、故障恢复变化
- 配置 schema、默认值、环境变量、CLI 参数和覆盖顺序变化
- 构建脚本、代码生成、部署文件或 CI 工作流变化
- 测试覆盖范围、测试架构、关键验证路径和质量门变化
- 协议、驱动初始化、硬件交互或外部依赖的关键行为变化
- 已知限制、TODO/stub、已验证缺陷被新增、修复或推翻

通常不需要更新：

- 纯格式化、注释排版或拼写修正
- 不影响公开行为和调用链的局部重命名
- 只修改测试断言文字
- 无行为、配置和构建影响的 patch 级依赖升级
- 不改变数据流、状态流、接口和风险的小型内部优化

即使判断“无需更新”，最终也要给出简短证据，而不是直接忽略。

## 更新映射

1. 新增、删除、移动模块或入口
   - 更新 notebook 模块摘要
   - 必要时更新 `01-program-structure.md`
2. 数据流、状态机、协议、驱动、异步任务变化
   - 更新 notebook 数据流/运行流摘要
   - 必要时更新 `02-data-flow.md`
3. 配置、命令、部署步骤、构建行为变化
   - 更新配置加载链、运行流或参考资料索引
4. 测试、CI、质量门变化
   - 更新 notebook 测试/状态摘要
   - 必要时更新 `03-ci-pipeline.md`
5. 复杂模块、维护风险、风格约定变化
   - 更新风险或维护说明
   - 必要时更新 `04-code-style.md`
6. 缺陷修复
   - 删除已经失效的缺陷，或标记为已解决并附当前证据

## 推荐执行顺序

### 改动前

1. 调用 `check_notebook` 获取基线。
2. 如果 notebook 存在，先读它及本次相关的专题文档。
3. 读取 README、Agent 指南、设计规格和计划，避免重复造文档。
4. 通过源码和搜索确认当前实现，不把 notebook 当成绝对真相。

### 改动中

- 当结构边界发生变化时同步记录受影响的文档章节。
- 代码事实与旧文档冲突时，以当前实现和验证结果为准，并修正文档漂移。
- 不为满足检查器而填入空标题、空图或无证据缺陷。

### 改动后

1. 查看实际 diff，而不是依赖记忆。
2. 对照“更新映射”逐项判断。
3. 更新必要文档并检查 notebook 的索引和摘要。
4. 再调用 `check_notebook`。
5. 读取被报告为可能陈旧的文件，确认是实际风险还是时间戳噪声。
6. 在最终回复中报告文档状态和未验证项。

## 陈旧检测

定期检查：

- 源码目录和 notebook 模块列表是否一致
- notebook 中记录的缺陷与限制是否仍成立
- `git log docs/program-notebook.md docs/architecture` 是否明显早于结构性源码变更
- notebook 是否引用不存在、重命名或过期的专题文档
- 配置、构建、CI 和测试说明是否仍与当前文件一致

时间戳只能表明“值得检查”，不能证明内容已经陈旧。

## 红灯信号

| 借口 | 应采取的行动 |
|---|---|
| “改动很小，不用判断” | 先确认是否影响接口、数据流、配置或风险 |
| “稍后统一更新” | 在当前上下文仍完整时完成判断和必要更新 |
| “只是重构” | 检查模块边界、调用链和所有权是否改变 |
| “文件太多，写不全” | 按模块分组，必要时拆分专题 |
| “插件已经提醒过” | 提醒不等于结论，必须读取证据 |
| “notebook 太长” | 保留摘要，把细节拆到 architecture docs |

## 常见维护错误

- 没有代码证据就写某功能缺失或存在缺陷
- 架构改动后只更新 README，没有更新 notebook 索引/摘要
- 新专题文档没有被 notebook 引用
- 用生成时间或文件 mtime 直接断言内容错误
- 把工具建议当作必须修改，而不读取相关代码
- 每轮重复注入 skill 或状态报告，造成上下文膨胀和缓存失效

## 最终报告模板

- Notebook 状态：已创建 / 已更新 / 已确认当前 / 无需更新 / 因只读、禁止写入或极简项目而未创建
- 专题文档状态：列出更新文件，或说明无需更新
- 检查证据：源码/配置/测试/Git/工具报告
- 变更章节：数据流 / 架构 / 运行流 / 配置 / 模块 / CI / 缺陷
- 未验证项：只列仍无法验证的事实
