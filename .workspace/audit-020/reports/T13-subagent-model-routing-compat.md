### 0.3 三条口径提示（避免后续轨道误读）

1. **「哈希全等」的作用域**：只覆盖两侧同名包的 `lib/`。**包的新增/删除**不在其中（例：`dsh-workflow-worker-thread` 在 A、B 两树**都不存在**，两份 churn 文件中**从未被比较过**〔0 命中〕——它的「零改动」是统计口径假象，正确表述是「**`0.1.5-rc.3` 之后即停发，0.1.7 时点已消失**」）。
2. **两条坐标轴不可混用**：本任务的*机制对比轴*是 `0.1.7 → 0.2.0`；但*要搬的配置内容*来自**现役 0.1.1**。凡「0.1.1 → 0.1.7 期间已经发生的破坏性变更」，在 0.1.7→0.2.0 轴上是「推定未变【H】」，在迁移轴上却仍是**必改项**。§6 对每条都标注了所属轴。
3. **`package.json` 的 `modified` 不等于代码改动**——`MEASURED-BASELINE.md §4` 的提醒正确；但反过来也要注意：**`modified` 也未必就是 `package.json`**（`dsh-agent-preset` 的 6 个里 5 个是文档/技能文件）。判定的唯一可靠口径仍是 `lib/`。

## 1. 结论摘要

1. **上游派发决策链 0.1.7 → 0.2.0 零变化【H】**。`@deepseek-ai/dsh-tool-subagent` 的 `lib/` **逐字节相同**（整包唯一差异是 `package.json` 版本串）；`dsh-subagent`、`dsh-agent-preset`、`dsh-agent-preset-registry`、`dsh-agent-default-model`、`dsh-subagent-fork-in-process`、`dsh-subagent-spawn-in-process`、`dsh-tool-subagent-control`、`dsh-settings`、`dsh-persona`、`dsh-client-ui-settings-subagent`、`dsh-client-ui-agent-preset`、`dsh-client-ui-subagent`、`dsh-agent-tool-presentation`、`dsh-tool-present` 同为 `lib/` 零改动（其中 `dsh-subagent` 与 `dsh-agent-preset-registry` 各有 1 个 `lib/typert.host.js`，经复核为非行为改动）。⇒ **本次迁移无需为「子代理模型路由」重新理解上游逻辑**。

2. **但「subagent 默认模型 = settings 段」从来不是上游能力，而是现役部署的本地补丁【R】**。现役 `~/.dsh/profiles/node_modules/@deepseek-ai/dsh-tool-subagent/lib/index.js` 是**被改造过的副本**（sha256 `65288049…` ≠ 上游 `26a1e804…`，73 行差异）：新增 `effectiveConfiguredAgentOptions()` `:119-136`（读取点 `:123` = `settings.get("dsh-subagent")`），并在派发处 `:530` 调用。**A、B 两树上游均无任何 settings 读取**（`grep` 0 命中）。⇒ 该行为**不会随升级自动继承**。

3. **`@local/dsh-subagent-model` 有 5 条核心假设不成立，其中 2 条在 0.1.7 时点就已断裂**：`@deepseek-ai/dsh-settings` 的 `installSettingsSection` / `settingsNamespace` 导出消失（0.1.1 有 → 0.1.7 起无，0.2.0 同【H】）；settings 面改为「**profile 条目 id** + 插件 Config 表单」；客户端 `settingsScope` 服务在 A、B 两树 0 命中；`peerDependencies` 显式排除 `<0.2.0`；宿主读取钩子不存在于上游。⇒ **必须重写（宿主半 + 客户端半 + 宿主补丁三处），不能原样搬运。**

4. **官方内置能力与本地定制正交，不可退役【R】**。0.2.0 官方内置 `subagent-model-selection-settings`（`subagentModelSelection` 服务，`{enabled, allowedModels}`）与「子智能体」设置页，管的是「**是否允许模型每次调用自选** provider/model + 白名单」；官方文案自陈关闭时「Subagents use configured defaults or inherit the parent agent's model」——**官方没有「子代理默认模型」这一设置项**。

5. **「subagent 默认模型 = settings 段」在 0.2.0 上不能原样保持**。`settings.yaml` 在 0.1.7 起已沦为**一次性导入源**（导入后改名 `.imported`，段名按 profile 条目 id 寻址 ⇒ `dsh-subagent:` 找不到同名条目、导入失败仅 `logger.warn`）。**替代方案见 §7.2**：方案 A（宿主补丁 + 插件重写）可完整恢复；方案 B（preset 静态 `agentOptions`，零补丁）为降级（改模型 = 重开会话）。

6. **preset 迁移：机制面可直接按「推定未变」处理，真正的必改项只有 3 类** ——（i）目录式 preset 已被废弃（0.1.7 起，非 0.2.0 新变）；（ii）两个字段级破坏项（`persona.text→prefix`、`workflow-worker-thread` 包已消失）属 **0.1.1→0.1.7 轴的历史漂移**，在 0.1.7→0.2.0 轴上均已「推定未变」但**对迁移仍是硬约束**；（iii）行 id 改名 `agent-presets → agent-preset-registry`。

## 3. 决策链结论（0.2.0 与 0.1.7 对比）

### 3.1 上游链（0.1.7 ≡ 0.2.0，`lib/` 逐字节相同）【H+R】

### 3.2 「settings 段覆盖」来自本地补丁（现役 0.1.1 专有）【R】

### 3.3 结论

- **机制对比轴（0.1.7 → 0.2.0）：上游派发决策链零变化**【H】。

## 7. 行为保持结论与替代方案

### 7.1 直接回答：**不能原样保持**

「subagent 默认模型 = `settings.yaml` 的 `dsh-subagent` 段」在 0.2.0 上失效，原因**不是** 0.2.0 改了相关代码（这些包 `lib/` 零改动【H】），而是**两个机制在同一条迁移轴的更早位置就已消失**：

1. **数据面**（断点在 0.1.1→0.1.7）：settings 面 = 「profile 条目 id + 插件 Config 表单」，`settings.yaml` 沦为一次性导入源并在导入后**改名** `.imported`（`dsh-settings:346-363`）；`dsh-subagent` 段因无同名条目而**导入失败（仅 warn，值只留在改名文件里）**。
2. **读取面**（断点在现役部署自身的补丁）：上游从不读 settings（A/B 两树 `grep` 0 命中）；现役能生效靠的是 `~/.dsh/profiles/node_modules/…/dsh-tool-subagent/lib/index.js` 的 **73 行本地补丁**，0.2.0 是全新安装，补丁不继承。

⇒ 不作处理则**退化为 preset 静态 `agentOptions`**；若迁移时漏掉 `agentOptions`（如官方 `standard` preset 那样留空），子代理会**继承父会话模型**——这是与现役差异最大的行为回退。

### 7.2 替代方案

#### 方案 A（推荐）：重写本地插件 + 对 0.2.0 重新落宿主补丁 —— 恢复「热 + settings 面可调」

**改动点 1 · 宿主补丁**（恢复读取面）
- 文件：0.2.0 安装树内 `<B>/dsh-tool-subagent/lib/index.js`（该文件相对 0.1.7 零改动【H】，故补丁点可直接沿用下列 0.2.0 行号）
- 改动：
  - 在 `hasConfiguredLlmSelection`（`:104-106`）之后新增等价函数 `effectiveConfiguredAgentOptions(runtimeCtx, configured)`，**读取源改为本地插件注册的服务**（如 `runtimeCtx.get("subagentDefaultRoute")`），语义与现役补丁逐条一致（非空串覆盖 / 缺失键保留 preset / 读取失败静默回退不抛）
  - 在 `execute()` 内先取 `const effectiveAgentOptions = effectiveConfiguredAgentOptions(runtimeCtx, config.agentOptions);`，随后替换 **`:495`** 的 `config.agentOptions` 与 **`:498-499`** 的 `...config.agentOptions` / `: config.agentOptions`
- ⚠️ **不可字节复制 0.1.1 补丁**：0.2.0 的 `execute()` 用 `runtimeCtx.subagents.resolveMaxDepth(config.maxDepth)`（`:508`）等，与 0.1.1 补丁所依赖的上下文（如 `typeof config.maxDepth === "number" ? … : void 0`、`config.toolName ?? "subagent"`）不同。**须针对 0.2.0 文本重新落补丁**
- 前置校验：不触碰 `lib/invariant.js`；补丁后 invariant 检查仍通过

**改动点 2 · 本地插件宿主半**
- 文件：`~/.dsh/profiles/node_modules/@local/dsh-subagent-model/lib/index.js`
- 删除 `installSettingsSection`/`settingsNamespace` import（A1/A2）；`Config` 两字段按需加 `.volatile()`（A3）；`apply` 改为注册服务 `subagentDefaultRoute`，`current()` 读 `this.config.<f>.get()`（A4，写法对照官方 `model-selection-settings.js:55-64`）；`DEFAULT_ROUTE` 与迁移后 preset 的 `agentOptions` 对齐（A5）
- 挂载行：`~/.dsh/profiles/web/cordis.patch.yml` 的 `insert` 行 `id` 即设置面命名空间；如需 `dsh-subagent` 就把该行 `id` 改成 `dsh-subagent`（官方无同名条目，无冲突）

**改动点 3 · 本地插件客户端半**
- 文件：`…/@local/dsh-subagent-model/lib/client.js` —— `inject` 去掉 `settingsScope`；改用 `settings.section` slot + `ctx.configForms.describe()` 与写回 API（对照 `dsh-client-ui-settings-subagent/lib/client.js:366,790-811`）；`llm-pi-ai` 模型清单来源按新 API 重定位
- 文件：`…/package.json` —— 放宽 `dsh-settings` peer range（A9）；调整 `dsh.client.inject`（A8）

**改动点 4 · 数据迁移**
- 把 `~/.dsh/settings.yaml` 中需保留的段逐条落到**对应 profile 条目**的 `config`（`cordis.patch.yml`）；`dsh-subagent: {model: deepseek-v4-pro}` → 迁入本地插件挂载行 config（方案 A）或 preset 的 `agentOptions`（方案 B）
- **先备份**：`dsh-settings:346-363` 会在首次启动时把 `settings.yaml` 改名为 `.imported`，之后核对该文件里哪些段未被导入

#### 方案 B（零宿主补丁，降级）：preset / 条目静态路由
- 改动点：把 `agentOptions: {provider: adam, model: <目标>}` 写进迁移后 preset 声明的 `tool-subagent` / `tool-subagent-fork` 两行（字段**推定未变【H】**，可直接搬）
- 行为差异（须如实标注）：改模型需编辑 preset 声明，生效面 = **新会话**（`register()` `:500-524` → `activate()` `:525-545` 为新声明生成新 generation/standing mount；已在运行的会话与子代理保留旧 revision）——**不是**「改完下一次派发即生效」；也无法经设置页切换

#### 方案 C（正交增强，可叠加）
- 打开官方 `modelSelectionSettings: true`（Config `:255`），在 `subagent-model-selection-settings` 配置 `allowedModels` 白名单，让模型每次派发自选。注意：不是「默认模型」的替代品（§5.2），且只有 `enabled=true` 时 `list_subagent_models` 才注册（`:389`）

### 7.3 方案选择建议

| 目标 | 方案 |
|---|---|
| 完整恢复现役行为（settings 面可调 + 改完对后续派发热生效） | **A** |
| 只要求「子代理固定某模型」，可接受改完重开会话 | B（最少改动，明确降级） |
| 希望模型按任务自选子代理模型 | C（叠加于 A 或 B） |
