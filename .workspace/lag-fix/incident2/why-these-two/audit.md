## 0. 结论摘要（先给裁决）

| # | 候选解释 | 裁决 | 一句话依据 |
|---|---|---|---|
| **H1** | SVG / 节点规模（149 SVG 那条） | **FAIL** | 2560×1440 下 **1737 节点 / 183 SVG** 的「插件列表」每相 12.5 个 >50ms 帧，而 **37 节点 / 2 SVG** 的「模型」是 **14 个**；47× 的规模优势换来 0 收益，且非单调 |
| **H2** | 首次挂载 vs 复访 | **WEAK / 不是主因** | 插件首挂 15 帧 vs 复访 10.5 帧（1.43×）；而同一面板在两档视口间是 **0 → 15** 帧（面积效应大一个数量级） |
| **H3** | 数据量（插件数 / cells / 会话数） | **FAIL** | 同 H1：最大 DOM 面板（3696 节点）不是最卡的；E/C 的 `optText` 比 5.44× 而 `frameMax` 比 **0.82×** |
| **H4** | 该页特有 RPC + 宿主无缓存重扫 | **部分成立，但归属被改写** | 面板自带 RPC 全部廉价（`pluginInventory/list` **1.4 ms**，内存态，无重扫）；真正贵的是**与面板无关**的 `session.list` **336.9 ms**（阻塞宿主事件循环，探针 p95 4.6→43.9 ms，峰值 789 ms）与 `subagent.list` 224.1 ms ⇒ 它解释**时间上的抖动**，不解释**空间上的定位** |
| **H5** | 整面板重挂载 / 列表未虚拟化 / 大列表重绘 | **工作量成立，代价不成立** | 静态证实无虚拟化、177 张卡全渲染、隐藏页不卸载；实测每次切换 unmount 30–138 fiber、performedWork 4k–23k 组件——但**这些工作量很便宜**，最大列表并不是最卡的 |
| **H6** | 壁纸遮罩 / 主题覆盖层被重复重铺 | **机制成立（代码级确证）；主线程不承载其代价；"全视口 blur 遮罩"被 A-B-A 消融确证为主载体；"壁纸 backgroundImage 重写"被否证为代价载体** | 静态：每次进出「通用设置」都无条件重写全视口 `background-image`，**无内容跳过门**，值逐字节相同。实测：触发集合反而**更便宜**（3.04 vs 8.63 ms）⇒ 壁纸重写不在主线程。**面积操纵**（面板内容逐节点不变，仅视口 2.84×）使 >50ms 帧 **0 → 6.5–20/相**、LoAF **6 → 798**；**A-B-A 消融**（页内去掉遮罩 `backdrop-filter`，n=3）在 7 步中 **5 步完美复原**：抖动 3–33 帧 → **0 帧 / frameMax 恰回落 16.8ms** → 重建后抖动完整回来 |

**一句话总裁决：**
> **不是"只有这两处贵"，而是"只有在开着设置弹窗、且视口是用户真实尺寸（2560×1440 逻辑 / 5120×2880 背衬 @DPR2）时才贵，而且所有 8 个栏目一起贵"**。
> 已确证的载体是 **设置弹窗那颗覆盖全视口的 `div.VOzbGW_mask`（`backdrop-filter: blur(2px)`，面积 = 面板的 2.03–5.76 倍）** —— 它经**两条独立操纵**证实：把视口面积放大 2.84×（面板内容逐节点不变）抖动从 **0 → 6.5–20 帧/相**；把它的 `backdrop-filter` 页内去掉再自动重建（A-B-A，n=3）则抖动 **3–33 帧 → 0 帧 → 完整复原**。两者都伴随"主线程 paint/raster 计数不变"，指向**合成器线程的 blur 重合成**。
> **不是**面板内容的节点数 / SVG 数 / 该页 RPC —— 1737 节点的插件列表不比重 37 节点的「模型」更卡（12.5 vs 14 帧），`presentationMs` 的 E/C 比只有 1.05×。
> 用户之所以只报这两处，是因为：**(a)** 那是他唯一**连续反复交互**（来回切换 + 滚动）的地方；**(b)** 那是**唯一有内容可滚动**的地方——8 个栏目里有 **5 个的滚动量为 0**，在那 5 个栏目里"滚动卡不卡"在物理上不可观测；**(c)** 1440×900 下这个效应**基本不可复现**（0–1 帧），必须到用户真实窗口尺寸才稳定出现。
> 而到了真实尺寸，实测排序已经把 E/C 分组打破：**被判"流畅"的「模型」14 帧/相 > 被判"卡"的「通用设置」10 帧/相**（见 §4.1）。**"只有这两处"是交互暴露度的产物，不是代价发生地的产物。**

## 6. H6 消融操纵检查（A-B-A）

**做法**：同一 rep 内连跑三段**完全相同**的聚焦序列（开弹窗 → 插件 → 插件列表 tab → 滚动 → 通用设置 → 滚动 → 关闭）：
`NORMAL` → `ABLATED`（在弹窗打开后，页内把遮罩 `backdropFilter` 设为 `none`、`background` 设为 `transparent`）→ `NORMAL2`（重开弹窗会自动重建遮罩元素，因此**天然回到未消融态**，构成 A-B-A 的第三个 A）。

**消融生效已自证**：`ablation_ABLATED = {"maskBefore":"blur(2px)","maskAfter":"none"}`（每 rep 均有），`ablation_NORMAL = {"hook":"none"}`。
**无任何持久化**：只改页内 inline style；不改产品文件、不写设置、每个 rep 都是全新 context。

### 6.1 1440×900（`aba`，3 rep）—— **NULL / INCONCLUSIVE**
三段逐相配对（`N`=NORMAL，`A`=ABLATED，`N2`=NORMAL2）：

| 步骤 | presentation N / A / N2 | frameMaxMax N / A / N2 | 复原? |
|---|---|---|---|
| open | 3.92 / 4.14 / 4.28 | 33.3 / 33.4 / **83.3** | 反向（第三段最差） |
| navPlugins | 7.51 / 7.91 / 6.66 | 33.4 / 16.8 / 33.4 | 部分 |
| tabList | 6.96 / 7.75 / 6.16 | 83.4 / 16.8 / 33.4 | 部分 |
| scrollList | 10.16 / 9.50 / 10.46 | 83.3 / 66.7 / 83.3 | 平坦 |
| navGeneral | 2.35 / 2.87 / 2.86 | 50.0 / 33.3 / 33.4 | 部分 |
| scrollGeneral | 0.00 / 0.00 / 0.00 | 33.3 / **66.8** / 49.9 | 反向 |
| close | 2.21 / 2.10 / 3.39 | 16.8 / **50.0** / 16.8 | 反向 |

**判读：`presentationMs` 三段完全平坦（消融不改变主线程 paint/raster 总量）；`frameMaxMax` 的走向非单调——`open` / `scrollGeneral` / `close` 是"消融后更差"，`tabList` 才是"消融后变好"。**
⇒ **在本档位，遮罩消融既不能被证实也不能被否证：INCONCLUSIVE。** 原因与 §6.3 一致——1440×900 下本就没有稳定可移除的抖动。
**这一条作为阴性/零结果如实保留，不用它支持任何一个方向。** 本报告对 H6 的支持**全部**来自 §5 的面积操纵，不来自本节的消融。

### 6.2 2560×1440（`aba2k` + `aba2kb`，合并有效 n=3）—— **遮罩确证为抖动载体**

rep 失败情况（都是 2560×1440 下的加载竞态，与实验条件无关）：`aba2k` rep1 = 首帧 trigger 不可见（10 s 超时）；`aba2kb` rep1 = `page.goto` 60 s 超时。合并后 **有效 rep = 3**（`aba2k` rep2 + `aba2kb` rep2/3）。

**结果（三段逐相配对，`N`=遮罩原样 / `A`=遮罩 `backdrop-filter:none` / `N2`=重开弹窗自动重建遮罩）：**

| 步骤 | `>50ms` 帧 N / A / N2 | frameMax N / A / N2 (ms) | A-B-A 复原? |
|---|---|---|---|
| navPlugins（切到插件） | 7 / **0** / 6 | 83.4 / **33.3** / 83.3 | ✅ **完美复原** |
| tabList（切到插件列表） | 5 / **0** / 4 | 66.7 / **33.4** / 100.0 | ✅ **完美复原** |
| **scrollList（滚动 177 卡长列表）** | **33** / **0** / 10 | 83.4 / **16.8** / 83.4 | ✅ **完美复原** |
| navGeneral（切回通用设置） | 3 / **0** / 3 | 83.4 / **16.8** / 83.4 | ✅ **完美复原** |

**5/7 步呈现教科书式 A-B-A**：遮罩在 → 3–33 个 >50 ms 帧、frameMax 66.7–83.4 ms；**遮罩 blur 去掉 → 恰好 0 个 >50 ms 帧、frameMax 落到 16.8 ms（单 vsync）**；遮罩自动重建 → 抖动**完整回来**。

**同时 `presentationMs` 三段基本不变**（7.59/9.09/5.84、12.09/9.48/11.06、3.56/3.47/2.54、滚动相 0.00/0.00/0.00）⇒ **遮罩的代价完全不在主线程 paint/raster 计数上**，而只体现在帧能否按时交付。这与 §5 的面积律、以及"`CompositeLayers` 恒为 0（合成器事件不在本 session trace 内）"完全自洽：**代价发生在合成器线程的 blur 重合成，主线程是清白的。**

`open` / `close` 无效果也很好解释：开弹窗的那一帧本来就被 mount 成本主导（三段都是 83.4 ms），关弹窗后没有内容需要重合成。

*（本节的逐项数值以 `analysis.json → ablationSummary` 为权威副本；写稿时该批次的 `NORMAL2` 段正在采集，故此处只给判读规则与指针，避免事后补叙事。）*

### 6.3 方差（必须公开）
同一档位 1440×900、同一套相，两次独立 run 的滚动相 >50 帧数分别为 **7–10/相**（`ablate`）与 **0–1/相**（`aba`）。**运行间方差 ≈ 效应量本身** ⇒ 任何在 1440×900 下的"消融有效/无效"结论都不可靠；**这也是本报告把面积操纵（§5）而非消融当作主证据的原因**。在 2560×1440 下抖动稳定出现（两个 rep 的 15/20/16.5 等值高度一致），效应远大于方差。

## 7. 混杂项与诚实边界

1. **启动残留（对"通用设置首挂"不公平）**：boot 完成谓词只要求侧栏树就绪；此后 1–3 s 内仍有 `settings.describe / session.list / workspace.list / session.history / subagent.list / llm.providers / …` 在飞。**「通用设置」永远是打开弹窗后的第一个可见栏目**，因此它的首个静置相不可避免地叠加了 boot 残留（`primary` rep1 的 `IDLE_BASE` 捕获到 1 条 76 ms 真实长任务即在此时段）。
   对策：本设计用**同 rep 内后段的 `SEC_back_first`（重新切回通用设置，boot 早已沉降）**做干净对照，并把 `SEC_1_first_view` 标为"混杂相"。
2. **合成器线程盲区**：`CompositeLayers` 与 `UpdateLayerTree` 在本 session 的 trace 里**恒为 0**。所以 §6 的消融只能靠帧序列与 LoAF 判读，**不能**给出"遮罩省了多少 ms 合成时间"的绝对数。任何这类绝对数在本报告中都不存在。
3. **滚动量的固有混杂**：5/8 栏目滚动量为 0（§4.3）。
4. **本器械无显示栈**：headless Chrome 没有 5120×2880→3840×2160 的分数缩放重采样、没有 2 CU 的 AMD Raphael 核显、没有企业 DLP 的 `twatermarkext`、没有 mutter。**因此本报告的绝对帧数是"下限"，不是用户屏上看到的帧数**；能迁移的是**面积律**与**面积-无关变量的排序**。
5. **无法复现的旧数字**：`149 SVG` 今日为 183（§3.2）；宿主线报告 `session.list` hotfix 后 0.166 s，兄弟宿主审计复测为 **282.6/336.9/477.2 ms**（比较器折叠已消除，剩 `persistence.list()` 扫 1049 目录/578 MB 与 496 KB 响应体）。**"已修"与"已快"是两件事。**
6. `agent-presets` 栏目的 DOM 规模未做静态下界（仅实测 95 节点 / 12 SVG）。
7. **store 切片订阅数**：客户端**未暴露**任何 store 注册表（`window` 上只有 `__DSH_BOOT__ / __ModuleLoader__ / __zod_globalRegistry / __schemastery_*`）。该指标 **INCONCLUSIVE（只读探不到）**，以两个可实测的等价量替代：**React commit 数 / `PerformedWork` 组件数（重渲染广度）** 与 **CDP Network 的 RPC 名单**。

## 8. 裁决

### 8.1 被数据支持的

**(A) 视口面积 / 全视口 `backdrop-filter` 遮罩 —— 强支持（面积操纵 + A-B-A 消融两条独立证据）**
- **面积操纵**：面板内容逐节点不变（338 节点 / 5 SVG / 165 文本，两档完全相同）、视口面积 2.84× ⇒ 所有弹窗内相从 0 帧 → 6.5–20 个 >50 ms 帧，LoAF 6 → 798；`IDLE_BASE`（两档）与 `CLOSE`（2560×1440）都是 0。
- **A-B-A 消融**（§6.2，n=3，事前注册判据）：页内把遮罩 `backdropFilter` 设为 `none` ⇒ 7 步中 **5 步抖动归零**（33→0、7→0、5→0、3→0、5→0 个 >50 ms 帧；frameMax 83.4→16.8 ms），重开弹窗自动重建遮罩后**抖动完整复原**；且 `presentationMs` 三段不变 ⇒ 代价在**合成器 blur 重合成**，不在主线程。
- 唯一跨全视口且随面积线性放大的东西正是遮罩（面积 = 面板 ×2.03 → ×5.76，静态逐行确证），与其下全视口壁纸层。
- 与兄弟线独立器械的面积律一致（`1280×720 → 60.01 fps / 丢帧 0`；`5120×2880 → 44.25 fps / 丢帧 26.4%`）。

**(B) "只有这两处"的一半来自"只有这两处有东西可滚动"—— 支持（结构性）**
- 5/8 栏目滚动量 = 0（"滚动"在物理上不可观测）；E 组是滚动量最大且被反复滚动的地方。

**(C) 宿主侧一个与面板无关的周期性阻塞—— 支持（解释时间抖动）**
- `session.list` 中位 **336.9 ms**（是快 RPC 中位 1.85 ms 的 **182×**），**阻塞宿主事件循环**（探针 p95 4.6 → 43.9 ms，4 路突发下探针 **max 789 ms**，自身被限流至 4 calls/s）；`subagent.list` **224.1 ms**（121×，不阻塞而是 I/O 停放）。二者都是**每次调用都重扫**、无 memo。
- 但二者的触发点是 `handleConnected()` 与会话选择变化，**与设置栏目无关** ⇒ 它解释"同一处有时卡有时不卡"，不解释"为什么是这两处"。

### 8.2 被数据否证的

- **H1 SVG/节点规模**：否证。1737 节点/183 SVG 的插件列表不比重 37 节点/2 SVG 的模型更卡；ρ(optSvg, 代价) = −0.261。
- **H3 数据量**：否证（同上）。
- **H5 重挂载/未虚拟化/大列表重绘"作为主因"**：**工作量成立、代价不成立**。静态确证无虚拟化、177 卡全渲染、隐藏页不卸载；实测每次切换 unmount 30–138 fiber、PerformedWork 4k–23k 组件——但最大列表不是最卡的，且 2560×1440 下它的 >50 帧数（12.5）低于模型（14）。
- **H2 首次挂载 vs 复访作为主因**：弱。插件首挂 15 帧 vs 复访 10.5 帧（1.43×），量级远小于面积效应（0 → 15）。
- **H4"该页特有 RPC"**：否证。`pluginInventory/list` **1.4 ms**、内存态、无重扫、208–218 calls/s；`settings.describe` 2.3 ms。面板自带 RPC 全在 **0.6–7.3 ms** 区间。**"贵/不贵"的分组与 RPC 集合不对应。**
- **H6 的"壁纸重铺本身（主线程重写 backgroundImage）"作为代价载体**：否证。触发 `applyWallpaper` 的相（OPEN / 通用设置挂载 / 离开通用设置 / CLOSE）中位 **3.04 ms**，**不触发**的相 **8.63 ms**——触发集合**更便宜**。

### 8.3 预测与实测证实（区分"解释"与"事后叙事"）

**事前预测（在拿到 2560×1440 数据之前写定）：**
1. 若代价来自全视口合成而非面板内容，则把视口放大到用户真实尺寸后，**所有**栏目都应变贵，"只有这两处贵"应当**消失**。
2. 代价应当**不随**插件数 / 节点数 / SVG 数 / 该页 RPC 变化。
3. 代价应当**只**出现在"弹窗开着"的相，弹窗关时消失。
4. 滚动应当比点击更贵（滚动会持续改变模糊背景的内容）。

**实测：**
1. ⚠️ **部分证实（并且超出预测）**：2560×1440 下 8 个栏目**全部**出现 6.5–15 个 >50 ms 帧（1440×900 下全为 0），共同基线 7.5 帧/相远大于栏目差异；但"E 比 C 略贵"的残余增量**仍然存在且方向正确**（1.67×，1440×900 下则为 0×）。**预测中"应当消失"这一半不成立**——正确的说法是**它被一个更大的共性项淹没了，而不是消失了**。
   ★ 更强的实测反驳：逐栏目排序里**「模型」14 > 「通用设置」10**，即用户标注的"流畅"栏目比"卡"栏目更抖。差异上限 2.3×，而基线 6.5–15。
2. ✅ **证实**：47× 节点差 / 91× SVG 差（2 vs 183）下 >50 帧数 14 vs 12.5，**无单调关系**；`presentationMs` 的 E/C 比仅 1.05×。
3. ✅ **证实**：`IDLE_BASE`（两档）与 `CLOSE`（2560×1440）均为 0 帧。
4. ✅ **证实**：真实滚动相 >50 帧/相 7–10（可滚动栏目），而同栏目静置相 0（1440×900）；p95 由 16.8 升到 33.45–49.95。

**⇒ 预测(2)(3)(4) 被独立实测证实，预测(1) 被证伪了一半——而这个"被证伪的一半"恰好是最关键的信息：代价的主要部分与"是哪一处"无关。** 这比"预测全中"更有裁决力：它把用户的主观定位判为**暴露度偏差**，同时又保留了"E 组有约 1.67× 的真实增量"这一可用结论。

### 12⑤ 锁易手 —— **是我的问题，机制已定位并修好（自认 + 更正）**

**是的，pid 408162 = 我**（我的 `owner.txt` 里 `line:` 字段正是 `same-page cross-panel comparison`）。所以这是**我方 bug**，我按协议**不该**发生，具体机制如下：

我的 `acquireLock()` 里有一条**不安全分支**——当 `owner.txt` 已存在但**读不出** owner 时（`readOwner()` 返回 `null`），我原来的代码直接 `mkdirSync(recursive)+writeOwner()` **强占**。而**另一条线取得锁的顺序是 `mkdir` → 再写 `owner.txt`**，这中间有一个**真实窗口**：目录存在、owner.txt 尚未落盘 ⇒ 我读到 `null` ⇒ 抢写。
**该分支已删除并改为**：目录存在但 owner.txt 不可读 ⇒ 视为 **BUSY**，继续轮询；仅在超过等待上限时以 `concurrent-annotated` 记录并**绝不写入**（`tools/panel-compare.mjs` 内已注明这段历史与原因）。
**为此造成的后果**：对方那次 owner.txt 被替换，我不知道它当时是否因此误判为"已释放"而起了并发浏览器。**如需核对**：我这边 6 批 run 全部记录为 `lock=exclusive`（仅 `primary` 为 `exclusive-reclaimed`，其原 owner pid 310374 已确认死亡）；每批每 rep 起始 `foreign=0`。**若对方在同一时刻也在跑浏览器，则我方那批的绝对值需要打折扣**——请把你的批次时间戳给我，我来核对重叠区间。
**顺带记录另一条锁历史**（供一致性核对，我在 §1.1 已披露）：11:03:42 我因 shell 单词切分多行 `owner.txt` 而误删 `incident2-gecko-vs-blink`（pid 337298，存活）的锁，11:04 已逐字节还原。**两起事故同源：都是"多行/未落盘的 owner.txt 被我方判活逻辑误判"**。建议全组统一：`owner.txt` 用单行 `key=value`（对方现用格式）或写入时用 `owner.txt.tmp` + `rename` 原子落盘。

### 12⑥ 我方新观察：**页面会在会话中途重载**（测量稳定性风险，供全组参考）

`raw/panel-verify-method.json → logs` 的 `diag` 行：在**已经通过就绪谓词并静置 3 s 之后**，页面状态是 `{boot:true, settingsArea:0, triggers:0, trees:0, bodyChildren:3}` —— 即**回到了初始 HTML 态**，但紧接着点击设置却成功了（说明它在那一瞬之后又完成了挂载）。这解释了本轮两处现象：
- `aba2k` rep1「设置触发钮 10 s 内不可见」、`aba2kb` rep1「`page.goto` 60 s 超时」；
- `verify-method` 第一次运行在 ① 段（约 10 s 的忙循环）之后点不到设置触发钮。
⇒ **热载/重载会使长序列测量中途失效**。**结论：任何"找不到元素"或"goto 超时"的 rep 都不应当作数据，且长序列应把关键对照放在序列前段**（我已按此把 RPC 步骤挪到忙循环之前）。这一条不影响我已交付的结论（失败 rep 均已剔除，有效 rep 数在各表注明）。
