### 0.1 对 ★ 的展开：为什么"点击后窗内有停顿"不等于"点击造成了停顿"

本批共 **5 次**「全新页面→点设置」。**必须如实说明：确实有运行在点击之后的窗口里出现了 ≥100ms 的停顿**，因此"点击窗内从来没有停顿"是**错的**。
但把同一次运行的**点击前窗**摆在一起看，停顿就失去了"由点击引起"的特征——
因为主机负载在 6 秒内近似恒定，点击前窗就是这次运行的自身对照：

| run | 工况 | 点击前窗 p50 / p95 | 点击±500ms p50 / p95 | 点击后 3s p50 / p95 | (点击窗p95 ÷ 前窗p95) | 点击后命中 | 触发RPC耗时 |
|---|---|---|---|---|---|---|---|
| 1 | LOADED | 28.5 / 85.9 | 28.3 / 56.4 | 22.5 / 54.8 | **0.66** | 1 | 638.0ms |
| 2 | HEAVY | 110.9 / 319.3 | 97.8 / 396.1 | 105.9 / 356.9 | **1.24** | 2 | n/a |
| 3 | HEAVY | 9.2 / 103.9 | 10.5 / 78.7 | 7.7 / 50.8 | **0.76** | 0 | 341.0ms |
| 4 | LOADED | 23.6 / 87.6 | 36.9 / 100.9 | 30.9 / 72.5 | **1.15** | 1 | 883.3ms |

读法：
- **run 4（最干净的一次"有命中"）**：点击窗 p95 = 100.9ms，而其**点击前窗 p95 = 87.6ms**（比值 1.15）；
  那次 109.3ms 的停顿发生在 **+463ms**，且 883ms 的宿主负载水平**在点击之前就已存在**（前窗 p50 = 23.6ms vs 之后 30.9ms，无台阶式变化）。
- **run 2 / run 5（命中 2 次的那两次）**：这是受外线争用最重的两次，**点击之前**宿主就已经在 100–620ms 量级上打转
  （前窗 p50 = 110.9ms / 148.7ms，命中 11 次 / 9 次 ≥100ms；run 5 更是一次 422ms 的停顿**从点击前 343ms 起就在飞**、横跨点击时刻）；
  它们的点击后高延迟与"点击"没有可分辨的因果特征。
- **run 1 / run 3（命中 0 次）**：点击窗 p95 反而**低于**点击前窗（比值 0.66 / 0.76）。
- run 2 / run 5 的"触发RPC耗时"为 n/a：这两次宿主争用最重、页内 RPC 时间线未能解析出 click-direct 配对（见 §2 的采样完整性说明），故不对该列作结论。
- 因此：5 次运行里"点击窗 p95 ÷ 前窗 p95"落在 **0.66 – 1.38**，与**宿主当时的负载水平**同步变化，
  而与"是否点击"没有稳定关系；**没有任何一次出现"点击后立刻台阶式抬升并持续"的形态**。

## 1. 方法、口径与纪律

### 1.1 心跳口径（为什么不是 `monitorEventLoopDelay`）
- 探针在**外部进程**，`perf_hooks.monitorEventLoopDelay` 测不到宿主事件循环；且该 API **会丢弃 `reset()` 后的第一个样本**
  （实测 3s/20s 阻塞只报 10.32ms/10.6ms，而同一时刻心跳空档是 2990ms/19993ms —— 证据 `.workspace/lag-fix/exec-ingest/out/eld-reset-trap.txt`）。
- 本档统一用**外部可观测代理口径**：串行、50ms 间隔、交替 `POST /api/host.describe` 与 `POST /usage/status`（正确 RPC 信封），逐拍记墙钟延迟与响应字节。
- 串行是刻意的：并发心跳会把"自造排队"混进延迟里。代价是相邻两拍真实间隔 = 50ms + 上一拍耗时，故分析一律按真实 `t0` 取窗。
- **排程行为已核验（很重要，否则会误读数据）**：本循环的 due 每拍只前进 50ms，
  而一次长拍会让排程欠账 ⇒ 之后循环以 **~1ms 间隔连发**把欠账补平（实测 run3 在 953ms 长拍之后出现连续 ~1.0ms 空档）。
  补平期间的空档 → 0，是**预期行为**，不是"探针被饿"。
  真正能区分"宿主慢"与"探针被饿"的是：**宿主慢 ⇒ 长拍出现在拍内耗时(`ms`)且拍间空档 <50ms；
  探针被饿 ⇒ 拍间空档本身变大**。本批三次运行的拍间空档最大值分别只有 49.3 / 49.4 / 49.3 ms ⇒ **停顿全部发生在请求等待里**。

### 1.2 时钟口径
- 页内与 Node 都用 `performance.timeOrigin + performance.now()`，**两者同处 epoch 轴**，无需插值即可直接比较；
- 换算残差由 `evaluate` 往返实测夹逼给出（见 §3 的"换算误差界"列），不假装零误差。
- ⚠️ 一个易误读的量：JSON 里的 `clock.deltaTimeOriginMs`（本次 73.3s / 182.0s / …）**不是时钟偏移**，
  它只是"本探针进程启动 → 建页"之间的等待时间差（主要就是在等共享探针锁）。三次运行实测：

```

1    13.6s                              ±0.61ms          -0.43ms
2    30.0s                              ±0.57ms          -0.75ms
3    165.3s                             ±0.70ms          -0.97ms
4    1.1s                               ±0.46ms          -0.75ms
5    31.8s                              ±0.50ms          -1.11ms
```

- 点击锚点取**页内捕获的真实 `pointerdown`/`click` 时刻**（同 epoch 轴、不受宿主停顿影响），Node 侧 `[tSend, tDone]` 夹逼仅作兜底与核对。

### 1.3 纪律
- 只打**只读**端点（`host.describe`、`usage/status`）；**唯一写操作**是 G1 允许的那一次 `POST /usage/refresh`；
- **未重启、未 pkill 宿主**；对不属于本线的进程一律不发信号（本档曾两次因 `pgrep -f` 自匹配而误杀自己的 shell，已在工具里改为 `/proc` 遍历 + 拆分字面量）；
- 浏览器**优先**持有共享探针锁 `research-v2/.probe.lock`（原子 mkdir、绝不清理他人记账、跑完立即释放）；
- **协调者裁决（2026-09-22，方案 c，立即生效）**：所有 incident2 浏览器线优先原子取锁，**取锁失败超过 3 分钟即可并发运行**，
  但必须落盘 `concurrentWith` 与当时 loadavg，且结论必须用**运行内 pre 窗对照**判读、**不得使用绝对阈值**；
  优先级 `minimal-page` ＞ `live-repro` ＞ 其他（本线属第二档）。本档据此对后段运行启用了 `--concurrent-after-s 180` 并逐次标注。
- 绝不 pkill 他人浏览器（发现异常只记 PID）；绝不强占/清理他人锁。

### 1.4 工具链自证（防止把"没采到"读成"零停顿"）
- `dryrun-tooling.mjs`：本地 mirror 页 7/7 PASS —— 证明 ① 页内 hook 真装上（unary RPC 走 fetch，WS 只承载事件流）② 点击锚点真采到 ③ 可见性信号真会从 false 翻到 true ④ 突变真被记录；
- `selftest-analyze.mjs`：合成 run（答案预先算好）15/15 PASS。**过程中抓到分析器两个真实缺陷**：
  1. 曾直接采信上游写好的 `summary` 而非从原始 beats 现算 ⇒ 上游口径漂移会被静默带入结论；
  2. RPC 方法名曾被 **HTTP 动词 `POST`** 冒充 ⇒ 会把"设置调用"误判成非设置路径。两者均已修复，修复后自证全绿。

- **查得到**：当前 PSI `cpu`/`io`/`memory` 的 some 与 full，avg10/avg60/avg300 **全为 0.00**（协调者独立核实一致）⇒ 此刻无系统级争用。
  这同时说明一件要紧的事：**历史上那些秒级停顿不是由 CPU/IO 压力指标能解释的**（PSI 为 0 时也可能出现），
  因此更应刻画为"某个进程内的阻塞等待"，而不是"机器过载"。

⇒ **判读铁律**：既然"宿主秒级停顿"在无点击时也出现，就不能用绝对阈值判定点击因果；
本档改用**运行内对照**（同一次运行内，点击窗 vs 其自身的 pre 窗）——宿主负载在 6 秒内近似恒定，pre 窗就是同条件的自身基线。

### 3.2 ★ 点击触发的那次 RPC「飞行区间」内的宿主心跳（决定性口径）

若点击真的把宿主卡住，那么**在它触发的那次 RPC 尚在飞行时**，宿主心跳必然出现尖峰。

```
run   RPC 方法                     发送(+ms)  响应(+ms)   RPC 耗时   期间心跳数  期间max   期间p50   期间≥100ms
1     agentPreset.list             4          642        638.0ms    13          112.1ms   27.8ms    1
3     agentPreset.list             4          345        341.0ms    24          75.6ms    7.5ms     0
4     agentPreset.list             4          888        883.3ms    18          109.3ms   36.6ms    2
```

**分辨率说明（重要，避免把"没采到"读成"没停顿"）**：心跳是**串行**的，一拍结束后才发下一拍；
因此一次 ~145ms 的 RPC 飞行区间内只能落 2–4 拍，恰好落在该区间内的 ≥100ms 尖峰**可能被漏掉**（漏检概率约 (145-100)/145 ≈ 31%，仅针对"刚好只放一次尖峰"的情形）。
所以 §3.2 的结论是**"未见 ≥100ms 阻塞"（否定性证据）**，而不是"已证明该区间内绝无阻塞"；
绝对口径请以 §3.3 的"点击 ±500ms 窗（20 拍）+ 点击后 3s（60 拍）"为准。

### 3.3 拍间空档 ↔ 上一拍耗时 的恒等式核对（探针侧自洽性）

## 6. 混杂因素与局限（必须与结论一起读）

0. **绝对阈值已被协调者与本档共同判定为不可用**：本机同时有 9+ 条 incident2 线在跑浏览器探针、宿主 web 进程自身 CPU 长期 ~75–80%，
   且"与点击无关的秒级停顿"已被独立证据确证（§A 静止基线 max 18.6s、≥100ms 占 8.8%）；
   故本报告**只以"运行内 pre 窗对照"和"比值/零值"立论**，凡是绝对 ms 数字都只作描述性参考。
1. **宿主工况在测量期间剧烈漂移**（§A）：本机同时有 9+ 条线在跑浏览器探针、宿主 web 进程自身 CPU 长期 ~75-80%，
   并观测到跨会话重命令。**任何绝对阈值判读都不可靠**，故本档以"运行内 pre 窗对照"为主判据，并给每次运行贴工况标签。
2. **探针自身即负载**：20 次/秒的只读心跳本身会给宿主 web 进程加压。本档据此把高频静止基线在点击测量前**停掉**，
   只保留 500ms 速率的哨兵，避免"用测量行为污染被测对象"。
3. **无进程内探针**：外部观察无法取宿主堆栈。本档在无法拿堆栈的前提下给出最强可得归因——
   把每一拍尖峰与"当时在飞的 RPC（方法名/发送时刻/响应耗时）"做时序关联（§5.1），从而能指名"当时在等谁"，
   但**不能**给出宿主侧调用栈。这是口径本身的边界，不是本次遗漏。
4. **`/usage/*` 首挂 9 路的时机**：本档测量的是"全新页面→点设置"路径；usage 面板的首挂 9 路只在打开 usage 视图时发生，
   点击设置路径并不触发（见 §4 表内实际捕获到的请求集合）。
