## 0.0 ⚠️ 并发污染裁决（协调者实测发现；**本节推翻本档此前对"持锁=独占"的默认**）

协调者实测：**跨线锁未被所有线遵守**（19 个 headless_shell 而锁为 free）。本档据此做了三项工作。

### (1) 每窗口并发记录 —— 已实装（`lib/tab-profile.mjs`）

从本版起，每个测量窗口在**起止两端各采一次并发快照**，随窗口落盘：

| 字段 | 含义 |
|---|---|
| `concurrency.atStart` / `atEnd` | 窗口两端并发快照 |
| `concurrency.exclusiveForWholeWindow` | 两端都无外来浏览器才为 `true` |
| `concurrency.maxConcurrentBrowserInstances` | 两端中较大的外来浏览器实例数 |
| `hostPid` / `hostAlive` | **宿主 PID 1390375** 及其存活状态（每窗记录） |
| `concurrentHeadlessShellProc` | 等价于 `pgrep -c -f headless_shell` **减去本档自身** |
| `otherBrowsers` | 外来浏览器的 pid 与 `--user-data-dir` |

计数口径：直接扫 `/proc/*/cmdline`（不 shell out）；"浏览器实例"= 含 `--no-startup-window` 的主进程（`pgrep -c -f headless_shell` 会把 zygote/gpu/renderer/utility 也算进去，故两个数都记）；**本档自身**通过"父进程 = 本 node 进程"识别，再按其 `--user-data-dir` 标记扣除。任一窗口出现外来浏览器即写入 `concurrency-not-exclusive` 无效理由。另新增 `--require-exclusive --max-attempts=N`：窗口被污染则**丢弃该次并重测该标签**（每次尝试都保留在 `retryAttempts` 里可审计）。

### (2) 历史批次的并发实况 —— 用进程启动时间做回溯取证

`lib/concurrency-census.mjs`（`raw/concurrency-census.json`）：对仍存活的每个 `headless_shell`，从 `/proc/stat` 的 `btime` + `/proc/<pid>/stat` 第 22 字段重建**绝对启动时刻**，凡是启动早于某批次结束的，该批次期间它必然存活。

| 批次 | 窗口 | 外来浏览器存活（下界） | 直接观测 | 裁决 |
|---|---|---|---|---|
| `unlocked` | 14:55–15:13 | 0（**回溯不可见**） | 批次进行中 `ps` **实测 ≥3 个并发 Chromium**；且本档自身泄漏浏览器 15:04–15:28 | **NOT EXCLUSIVE（被直接观测否证）** |
| `locked` | 15:44:41–15:55:16 | **≥1** | **pid 2104881（udd `…25ZbPn`）启动于 15:16:01，至今仍存活** → **覆盖该批次 100% 时长** | **NOT EXCLUSIVE（被进程启动时间否证）** |

> **回溯法的重要限制（本档自己踩到并纠正）**：`unlocked` 批次的回溯下界是 **0**，但那**不能证明独占**——期间启动又退出的进程在 `/proc` 里不留痕迹。本档最初让脚本把"下界 0"标成 `EXCLUSIVE`，已修正为**永不从下界认证独占**；该批次是被**当时的直接 `ps` 观测**否证的。
>
> 实测当前并发：`headless_shell` 进程 **24–26** 个、浏览器实例 **4** 个（全为外来）、锁由 `react-commit-audit` 持有而同时有 4 个外来浏览器 → **此刻锁依然被违反**。

### (3) 为什么**没有**再开一次"独占复测"

协调者已下令**全部线停止新开浏览器**（`MEASUREMENT-STATUS.md` §2），且独占在本机**经验上不可得**：另一条线在其 **1635 秒持锁期间实测"每窗 18–31 个外来 Playwright 进程、独占窗口 0/5"**。再加上本节 (2) 已**证明**本档持锁期间仍有外来浏览器存活。
→ 因此**再开浏览器既违反现行指令，也不可能拿到独占窗口，只会给其他线增加负载**。本档依协调者给的第二分支处理：**把该批数字标为"并发负载下采集、不可当基线"**（见 (4)）。
本档**没有**启动任何新浏览器来完成本次修订；本轮所有工作是纯读盘与 `/proc` 取证。

### (4) 两个批次一律标注

**`locked` 与 `unlocked` 两个批次的全部数字——尤其是绝对耗时类——一律标注为「并发负载下采集、不可当基线」。**
`analyze` 输出中固定携带：

```
concurrency.pollutionTier = "ALL-WINDOWS-POLLUTION-PRONE"
```

理由：本批次的**逐窗口并发计数当时没有记录**（器械是事后加的），回溯取证已否证两个批次的独占性。故**任何窗口都不得用于负载敏感型裁决**，只有结构性/计数型结论得以存活（见 §0.0.5）。

| | 无锁批次 | 持锁批次 |

即：**无锁批次的"模型/插件卡顿"是与并发探针负载共变的伪影**——它的基线本身就已经比持锁基线贵 2.3 倍。这正是跨线锁要防的错误，而它确实抓到了本档自己的一个错误结论。

### 0.3 持锁批次里那个唯一的例外：「子代理模型」——**未定性，不可作为结论**

它在持锁批次里是唯一饿死的标签，但**本档拒绝把它定性为"该标签自身有问题"**，因为反证同样硬：

- **同一标签在无锁批次里是最干净的之一**（54.4 fps，>50ms 帧 0.92/100，0/4 饿死）。
- **它自己的第一个窗口是完美干净的**：r1w1 = 59.5 fps、`>50ms` 帧 **0/595**、p99 16.8 ms、max 33.4 ms。
- **退化是突然开始并持续到批次结尾的**：r1w1 干净 → r1w2 40.5 fps（48/810 >50ms）→ r2w1 24.8 fps（55/248）→ r2w2 35.9 fps（67/717）；随后紧接着的 **plugins 的 return 窗口也退化**（48.4 fps、12/484 >50ms、LongTask 2）。
- **退化期间环境事件率极低**：r1w2=4.0/s、r2w1=0.9/s、r2w2=2.1/s —— 是**整个数据集里最安静的窗口**（基线 8.0/s，无锁批次基线 81.5/s）。所以**既不是 ambient churn 造成的，也不是它的反面能解释的**。

这四条合起来指向一个**时间性的、跨标签的退化事件（约 15:52:30 开始，持续到 15:55:16 批次结束）**，恰好覆盖了「子代理模型」的测量块并延续到 plugins 阶段；但它**不是持续的全局事件**（同一时段内 plugins 的 firstMount 是 59.1 fps / 0 个 >50ms 帧）。

**因此本档对「子代理模型」的定性是：一条需要专项复测的线索，不是已证实的标签属性。**
> **§0.0(2) 追加降级**：该批次的持锁期间**已证明存在 100% 时长的外来浏览器**（pid 2104881），故本条**进一步降级为"不可归因"**——连"线索"也只能在独占复测后才能成立。该复测依协调者指令**未执行**。 要定性必须做一次专门的、更长窗口的、持锁的重复测量（建议 ≥5 次重复、含跨该时段前后的对照），并把宿主侧事件日志与墙钟对齐。本档没有做这件事，也不声称已做。

### 0.4 「插件」标签专项（持锁批次）

- **首次挂载是 9 路 `/usage/*`（不是 8 路）**，全部 HTTP 200、`result.ok=true`、valid 9/9。
- **首挂载极其干净**：**59.1 fps、0 个 >50ms 帧（0/591）、LongTask 0、Script 20.3 ms、Recalc 4.1 ms**。

  → **这直接证明：宿主侧 `/usage` 排队延迟不是客户端卡顿源**，两者可完全解耦（宿主慢 2 倍，客户端照样满帧）。

- 回归窗口是退化的（48.4 fps）——落在 §0.3 那个时段内，同因未定性。

## 1.0 跨线测量纪律与锁状态

### 协议（实现于 `lib/lock.mjs`）

- **任何浏览器启动之前**必须取得独占锁：`mkdir .workspace/lag-fix/research-v2/.probe.lock`（目录创建在本文件系统上原子）。
- 锁存在时**每 20–40 s 重试，最长 30 分钟**；超时不启动浏览器、退出码 3、写 `LOCK-TIMEOUT.json`。
- `owner.txt` 记录 agent 名、**owner 进程 PID**、开始时间、purpose、token。
- **抢占条件**：owner 开始时间 >25 分钟**且**其进程已不存在；缺一不抢。
- 跑完 `rmdir` 释放；释放前校验 token，非本档持有的锁拒绝释放。
- 崩溃路径也关浏览器并释放锁（修掉了 §7.3 的泄漏）。
- 非浏览器工作（重算、画表、写文档）**不持锁**。

## 2. 判据（预先声明）与硬性陷阱

| 判据 | 阈值 | 说明 |
|---|---|---|
| 打开延迟可感 | `> 100 ms` | 用 `openMsClean`（变异精度）。`openMs` 为 rAF 量化（分辨率≈16.7 ms），仅交叉校验 |
| **帧率崩塌（主判据）** | 持续 `< 45 fps` | 基线 59.1 fps。低于 45 表示 rAF 跟不上，最贴近"用户可感" |
| 持续成本放大 | `>= 1.5x` 基线 ms/s | 绝对口径，仅在环境负载可比时有效 |
| 卡顿帧 | `>50 ms 帧 >= 3/100 且 > 基线 1.5 倍` | 基线 0.17/100 |
| 长任务 | 出现即记录 | 基线窗口 0 个 LongTask |

**四条硬性陷阱的处理：**

1. **`Performance.getMetrics` 是累计值 → 一律算窗口 delta。** 每窗保存累计原值 + delta；`analyze` 独立重算比对 → **42 窗口全一致、0 回退、0 issue**。
   > ⚠️ 交叉发现：既有 `reports/settings-jank-audit-live.json` 把**累计值**放进了看起来像窗口测量的字段（`ScriptDuration` 0.196→0.257→0.334→0.362→0.428→0.488→0.593→0.653 单调递增）。由它推出的"涨了 N 倍"都是该口径错误的伪影，**本档不复用该文件**。
2. **面板必须自证已装载**：内容容器（`[role="dialog"] nav` 的 `nextElementSibling`）节点 `>0` **且** `textContent` 相对点击前变化 **且** 活动标记移动到被点击 nav 索引。三者缺一即 INVALID。稳定后节点数：通用设置 777、模型 729、插件 1027、Agent 预设 787、远程工作区 741、分布式控制 708、vision-adam 717、子代理模型 761。
3. **切换失败标 NOT-FOUND，不标 PASS。** 主批次 16/16 run 为 PASS；tabMap 预扫中「通用设置」正确判 **NOT-FOUND**（它是默认标签，点它不切换，文本不变）——**语义正确，不是产品缺陷**；profile 阶段用"先 park 到模型再切回"绕开。
4. **invalid 原因落盘**：逐 run `valid`/`status`/`invalidReasons[]`，逐窗 `reasons[]`/`documentHidden`/CDP 原值/锁证明。
   > ⚠️ 已披露的采集器缺陷：窗口级 `reasons`（含 `frame-count-low`）**未**传播到 run 级 `invalidReasons`，存在"窗口被标记异常但 run 仍 PASS"。本轮不改写已落盘数据，而是在 `analyze` 中把"帧数偏低"重新解释为**卡顿证据本身**（帧率崩塌判据）并据此裁决。修复建议：直接并入。

## 5. 「插件」标签专项（主批次）

### 5.1 前置事实：`/usage/*` 的真实形态（侦察所得）

`/usage` **不是 `/api` 下的 RPC 路径，而是宿主根路径下的一族真实 HTTP POST**：`POST http://127.0.0.1:3080/usage/<summary|timeseries|heatmap|byModel|byProject|byDay|sessions|status>`。
请求体 `{"type":"client-request","rpcId":"<uuid>","method":"<m>","payload":{…}}`；响应体 `{"type":"server-response",…,"result":{"ok":true,"value":…}}`。

**有效性口径**：只有 (a) 有真实 HTTP 响应状态、(b) URL 是宿主 origin 的 `/usage/<method>` POST、(c) 响应体是 `server-response` 且 `result.ok===true` 才算 `valid`；裸 URL（无响应）、4xx（含 404）、`ok:false` 一律记 `invalidReasons`。**三个批次共 75 个样本（9+7+9）× 2 批次，全部 valid，无一条 invalid。**

### 5.2 首次挂载（含 usage 首次请求）

**实测 9 路，不是 8 路。** 持锁批次逐条：

| # | `/usage/<method>` | granularity | HTTP | 到首字节 | 到末字节 | 响应字节 | valid |
|---|---|---|---|---|---|---|---|
| 1 | summary | — | 200 | 145.38 ms | 145.28 ms | 270 | ✅ |
| 2 | timeseries | day | 200 | 200.52 ms | 200.45 ms | 932 | ✅ |
| 3 | heatmap | — | 200 | 225.41 ms | 225.28 ms | 1390 | ✅ |
| 4 | byModel | — | 200 | 254.97 ms | 254.56 ms | 950 | ✅ |
| 5 | byProject | — | 200 | 293.30 ms | 292.89 ms | 1041 | ✅ |
| 6 | byDay | — | 200 | 464.68 ms | 464.66 ms | 932 | ✅ |
| 7 | timeseries | hour | 200 | 482.29 ms | 482.23 ms | 775 | ✅ |
| 8 | sessions | — | 200 | 524.45 ms | 524.51 ms | **53 697** | ✅ |
| 9 | status | — | 200 | 528.43 ms | 528.26 ms | 310 | ✅ |

（口径：CDP `Network.requestWillBeSent`→`responseReceived` = 到首字节；→`loadingFinished` = 到末字节。首轮采集用 Playwright `request.timing()` 得到 `null`，已改网络栈时间戳。）

**9 路并发发出，宿主一路一路服务**：wall time 145 → 528 ms 单调爬升，末位在 ~528 ms 完成。这是**宿主侧排队**。

**关键**：同一窗口客户端 **59.1 fps、0 个 >50ms 帧（0/591）、0 个 LongTask、Script 20.3 ms、Recalc 4.1 ms**。
对照无锁批次：wall time 18 → 250 ms（**比持锁批次快 2.1 倍**），客户端 58.1 fps。
→ **宿主侧 `/usage` 延迟与客户端帧率完全解耦**（宿主慢一倍，客户端照样满帧）。**把"usage 首次 8/9 路请求"当作设置页卡顿根因不成立。**

## 6. 用户可感路径（诚实结论）

| 步骤 | 持锁批次实测 | 用户是否可感 |
|---|---|---|
| 1. 点"设置"打开面板 | `[role="dialog"]` 在 **2 ms** 内出现（`raw/locked/run.json → tabMap.opened.dialogAppearedMs`） | 否 |
| 2. 点某个标签（click→panel） | **6.6–12.8 ms**（8 标签 × 2 重复；tabMap 预扫 1.4–9.0 ms） | **否** |
| 3. 停留在该标签（0–30 s） | **7/8 标签 57.0–59.0 fps、0/4 饿死、>50ms 帧 ≤0.53/100**；仅「子代理模型」3/4 饿死 | 仅子代理模型（且未定性） |
| 4. 停留在「插件」 | 首挂载 59.1 fps / 0 掉帧；轮询周期 52.5–58.5 fps | 否（首挂载与轮询均不造成可感卡顿） |

**真的有 >50 ms 卡顿 / 长任务的步骤（持锁批次）**

- **「子代理模型」停留期**：3/4 窗口饿死（42.1 → 38.2 fps，最差 r2w1 24.8 fps / 55 帧>50ms 占 248 帧的 22%、p99 166.7 ms、max 333.3 ms），3 个 LongTask 之一也在此。
  **但同一标签在无锁批次里最干净，且它自己第一个窗口 0/595 掉帧** → **判为待专项复测的线索，不是已证实的标签缺陷**（见 §0.3）。
- 零星 LongTask：远程工作区（1）、分布式控制（1）—— 3 个样本，不按标签归因。

**其实很干净的步骤（不夸大）**

- **打开设置（2 ms）与切换标签（7–13 ms）** —— 不是问题所在。
- **通用设置、模型、插件、Agent 预设、远程工作区、分布式控制、vision-adam 七个标签** —— 帧率 57.0–59.0 fps、0/4 饿死、p95 16.8 ms，**与关闭设置时的 59.1 fps 同级**。
- **`/usage` 首次 9 路请求与 60 s 轮询** —— 宿主侧 145–528 ms 排队，客户端 59.1 fps / 0 掉帧。**宿主慢一倍，客户端帧率不变**，两者解耦。

**撤回记录**：早前"模型 4/4 饿死、是稳定复现重灾标签"的说法**已撤回**（§0.2）。它在持锁条件下 0/4 饿死、57.8 fps，与无锁批次的差异可完全由并发探针负载解释。

## 7. NOT-FOUND / INVALID 账目与可靠选择器

### 7.1 账目（主批次）

| 项 | 数 |
|---|---|
| profile run 总数 | 16（8 标签 × 2 重复） |
| PASS / INVALID / NOT-FOUND / ERROR | **16 / 0 / 0 / 0** |
| 重算窗口（含基线与 plugins） | 42 |
| **持锁窗口** | **42 / 42** |
| 累计指标回退窗口 | 0 |
| 采集期 delta ≠ 独立重算 | 0 |
| `/usage/*` 无效样本 | 0（首挂载 9 + 轮询 7 + 回归 9） |

**tabMap 预扫 NOT-FOUND（1 条，语义正确）**：`通用设置` —— 默认标签，点它不切换，`textChanged=false`、`activeMoved=false`，故判 NOT-FOUND 而非 PASS。**把"没有发生切换"记为通过才是错的。**

### 7.2 可靠选择器（附产品建议）

| 目标 | 可靠选择器 | 备注 |
|---|---|---|
| 设置对话框 | `[role="dialog"]` | 存在且唯一；class 为哈希（`VOzbGW_panel`）**不可依赖** |
| 标签导航容器 | `[role="dialog"] nav` | 8 个 `button` 子节点 |
| 内容/面板容器 | `[role="dialog"] nav` 的 `nextElementSibling` | 结构定位，抗 class 哈希变更 |
| 点标签 | `nav button:nth-of-type(n)`（索引）或文本匹配 | 见歧义警告 |
| 活动标签 | **无原生语义**，需推断 | 见下 |
| 面板自证 | 内容容器节点数 `>0` **且** `textContent` 变化 | 单一条件不足 |

**文本匹配歧义（实测踩到）**：`模型` 是 `子代理模型` 的子串，`has-text('模型')` 会命中 2 个按钮。可靠规则：**先精确匹配，再唯一子串匹配，不唯一则 NOT-FOUND 并输出候选**。本档两个批次各 16 次切换实际用到的策略为 `exact` 与 `unique-substring`（记录于 `runs[].nav.strategy`）。

**活动标签无原生语义（产品侧建议）**：实测 nav button 上 **`role="tab"` 0 个、`aria-selected` 0 个、`data-state` 0 个**（两批次一致）。唯一活动标记是哈希 class；本档用"class 字符串与全体按钮众数不同者即活动项"推断（`activeMarker.method="modal-class-differs"`）。
**建议加 `role="tab"` + `aria-selected="true"`**：既修可访问性，也让自动化免于依赖哈希 class。兄弟档出现过的 `tab-远程-NOT-FOUND` 即属**选择器缺陷**（用 `exact:true` 匹配短词"远程"，实际标签是"远程工作区"），非产品缺陷。

### 7.3 采集器已知缺陷（全部披露）

1. **窗口级 reasons 未传播到 run 级 `invalidReasons`** → 可能"窗口异常但 run PASS"。本轮把帧数偏低重解释为卡顿证据（帧率崩塌判据）处理；建议直接并入。
2. **首轮用 Playwright `request.timing()` 取 `/usage/*` wall time 得 `null`**（该 API 对这些请求返回 −1）→ 已改 CDP 网络栈时间戳并重跑 plugins 阶段。
3. **profile 阶段的 poll 循环缺 `mm.snap`** → 该阶段写 poll 汇总时 TypeError 退出，未产出 plugins 数据（无锁批次因此由两阶段合并而成，见 `raw/unlocked/run.json → meta.phases`）。
4. **崩溃路径不关浏览器 → 泄漏进程**（无锁批次泄漏 24 分钟）。**主批次已修**：`.catch()` 内先 `browser.close()`、再 `releaseLock()`、最后 `process.exit(1)`。
5. **锁元数据写错位置**：`result.meta.lock` 应为 `result.lock`，导致主批次在**所有阶段完成后**的末行崩溃（数据已逐窗 flush，未丢失）。**已修**（并镜像到 `meta.lock`，`analyze` 两处都读）。
6. **锁文件 `started_at` 时区标注错误**（UTC 数字 + `+08:00` 后缀）：已修并对在线文件就地修正；`started_epoch` 始终正确且为权威字段。
7. **日志时间戳为 UTC**（`run.stderr`/`locked.stdout` 前缀），而本文件行文用本地时间（UTC+8），相差 8 小时，交叉比对时需换算。
8. **`pkill -f playwright_chromiumdev_profile` 误伤兄弟档浏览器**（§3.3）。
9. **历史批次没有逐窗口并发记录**：并发器械是事后加的，因此 `locked`/`unlocked` 两个批次的**逐窗口外来浏览器数不可知**，只能用进程启动时间做下界回溯（且该下界**不能认证独占**）。这是本档**无法**给出 T1 之外的负载敏感结论的根本原因；后续任何批次必须用现成器械取证。
10. **跨批次比较同样不可信**：既然两个批次都受污染，"基线 Script 0.43×"这类比值只是"两次受污染观测之比"，不构成负载效应的证据。

## 8. 与既有结论的交叉核对

| 既有说法 | 本档证据 | 裁决 |
|---|---|---|
| 设置页自身不是单独的持续卡顿源；是外部事件流的放大器 | 持锁批次 7/8 标签确实帧干净（57–59 fps）；且**环境事件率与成本呈弱负相关**（−0.18/−0.33） | **支持"设置页通常不卡"**，但**不支持"churn 是放大器"**：子代理模型在 0.25 事件/s（全场最低）时掉到 42.1 fps |
| 首要残余机制 = `session/event → projection → list.set →` 下游渲染放大 | 34 窗口相关性弱负；vision-adam 0.5 事件/s → 58.9 fps，分布式控制 90.7 事件/s → 57.4 fps | **证据不支持**其为主导机制 |
| "已访问 settings tab 只隐藏不卸载，长期累积 DOM/订阅" | 16 次切换 `JSEventListeners` 242–273 **不单调增长**；各标签稳定节点数可重复（777/729/1027/787/741/708/717/761） | **本次未复现**（DOM/监听器层面）。订阅/timer 层面的保留无法由该指标排除 |
| 旧 live 探针的 per-tab 数字 | 存的是**累计值**且口径混淆（§2.1） | **不可作为对照** |
| usage 首次入插件会整段冻结 | 持锁批次首挂载 **59.1 fps / 0 掉帧**，而宿主 wall time 高达 145–528 ms | **客户端冻结未复现**；宿主侧延迟真实但与客户端帧率解耦 |
| 早前本档的"模型是稳定复现重灾标签" | 持锁复核 0/4 饿死、57.8 fps | **本档自行撤回**（§0.2） |
