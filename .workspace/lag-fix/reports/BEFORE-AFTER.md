**判读纪律（v1 声明但未真正执行，此处逐条落实）**：
1. `ws_rate_per_s` 必须与基线同量级才可比 —— 基线 73 帧/s；上表 ws 跨度 5.3–135.2，**绝大多数行不可与基线直接比**。
2. **N 是 O(N²) 机制的主变量**，v1 的主对比行同时含「代码补丁」与「数据缩容（N −69%）」两个变动 → **v1 的 −77% 无法归因于代码补丁**，本文件不再做该归因。
3. **帧类型口径不同**：基线的 WS 帧以 `session/event` 为主（20s 内 1309 帧），改后各次探针记录到的多为 `server-request`；分子语义不同，v1 未披露。
4. 同一状态的多次实测**跨度很大**（idle 16.4 / 27.5 / 45.0 / 45.3 ms/s）→ **单次测量不可作为门槛判定**，需固定条件 + 多次重复取中位数与区间。

## 二·bis、客户端算法修正的**可控基准**（与负载无关，可重复）

> 代码**不是手抄的**：两版 P1 清理代码分别从 pristine 备份与 live 补丁件中**程序化抽出**后基准化（`tools/bench-c1.mjs`，抽不到即报错）。这是端到端测量受负载限制时的确定性替代证据。

**反向印证 M2 诊断**：旧清理在 N=2361 每次 **5.22 ms**；基线实测空闲脚本 121 ms/s ÷ 该值 = **重建速率 ≈23 次/秒**（DIAGNOSIS 记录事件率约 65/秒，说明重建被合并或另有成本）——同量级，**定量支持 O(N²) 快照重建为主因**。
补丁后同一 N 下次成本 0.0838 ms ⇒ 即使 65 次/秒满速重建也只有 **5.4 ms/s**。

## 四、v1 未披露但影响结论的事实

- `reports/measure-after-C1.json`（15:37）的 `settings-open` 窗口**测量失败**（dom_nodes=108、panel=0，页面处于热替换中间态），v1 的证据表**跳过了该文件却未说明**。
- 探针曾有两处 bug（v2 已修）：`ws_rate_per_s` 分母用装置安装时刻（分子每窗清零）→ 系统性偏低；`session_list` 抓取缺 DSH RPC 信封 → 恒返回 680 B / `items:null`，**探针从不测量 N**。
