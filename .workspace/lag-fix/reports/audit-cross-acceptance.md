## 二、可比性纪律判定（核心）

文档自设纪律（`BEFORE-AFTER.md:4`）：「**必须先看 `ws_rate_per_s` 是否与基线 73 帧/s 同量级**，否则不能与基线数字直接比」。逐条判定：

| 判定项 | 基线 | 对照（主对比行） | 判定 |
|---|---|---|---|
| `ws_rate_per_s` 数值 | **73**（`measure5.json`） | **135.2**（`N734-active::windows[0]`） | ⚠️ **1.85×**。按文档自己的措辞"同量级"可勉强算过，但**方向是"改后更重"**（+85%），因此"更重条件下还更快"对结论有利——这本身是**有利于结论**的不可比，而非中性 |
| **帧类型构成** | `session/event` **1309**（65/s，占 90%）、`session/projection` 139、`tool` 127、`subagent` 44、`assistant/message` 9、`session/jobs` 1（`measure5.json::ws_by_keyword`） | **`{"server-request": 3385}`（100%）**——`measure-after-N734-active.json` 及**全部**四份 `measure-after-*.json` 的 `ws_by_type` **只有 `server-request`** | ❌ **分子口径不同**：一个是事件流（session/event 驱动 churn），一个是 HTTP-RPC 响应帧。**两者不是同一类负载**，"帧率同量级→可比"的前提**在类型维度上不成立**——文档从未披露这一点 |
| 会话规模 N | 2,361（`session_list.json`）/ 抓取 2,386 | 734（数据已删 1,670 条） | ❌ **N 从 2,361/2,386 降到 734（−69%）**。而 M2 的机制是**O(N²)**（`DIAGNOSIS.md:149`：「2361→500 约 22 倍」）。**N 本身是主变量**，主对比行同时含 **C1 代码补丁 + B2 数据删除** 两个变动 → **−77% 无法归因于代码补丁** |
| 每 20s 窗口的负载条件 | 会话活跃 + 流式（DIAGNOSIS §6 自述） | 活跃流式（ws 135） | ⚠️ 都"活跃"，但**活跃强度与类型都不同** |
| 是否存在同刻 A/B 对照 | — | **不存在**。没有"同一时刻、同一 N、同一活跃度"下的 before/after 配对；`compare()` 函数（`measure-after-C1.mjs:218`）本身就要求同 phase 才比，且**从未被使用过**（没有 `--baseline` 运行产物） | ❌ **−77%/−67%/−82% 三个结论建立在跨条件比较上** |

**逐条裁定**

1. **−77%（script 121→27.5）**：❌ **跨条件**。除 ws 1.85× 外，N 已降 69%，而 ≥2/3 的机制收益可归因于 N 下降（O(N²)）。**不可归因于补丁**。且文档把该行标为"可比条件下的结论"，只援引 ws 一项，**回避了 N 的变动**（N 就写在同一个表格里）。
2. **−67%（p99 100.1→33.3）**：❌ **跨条件同理**。另注意同一批数据里 `measure-after-C1-v2::idle`（N=2396，同规模）p99 = **33.3**——说明 p99 从 100.1 降到 33.3 与"N=734"无关，**这一条相对站得住**（C1-v2 是补丁后、数据未删，脚本 45.0 vs 基线 121.4 仍为 −63%）。**这是全套证据里最干净的一个对照：C1-v2::idle 45.0 ms/s @ ws 92.5 vs 基线 121.4 @ ws 73**——但文档没有把它作为主结论行，反而选了含数据删除的那一行。
3. **−82%（>50ms 帧 22→4）**：❌ **跨条件**（同上）。且 `measure-after-C1-v2::idle` 的 >50ms 帧是 **9**（N=2396 条件下），比基线 22 只降 59%，**勉强过 50% 门槛**——与声称的 −82% 差距很大。

**结论**：3 个百分数**算术全部正确**，但**可比性纪律未被真正执行**——只检查了 ws 一项（且方向有利），**未检查帧类型构成、未检查 N**。文档第 4 行标注"ws 135，比基线更重"是**事实陈述**，但把它宣称为"可比条件"是**过度授权**；正确的表述应是"某单一工况下观测到 X，工况与基线不完全可比，差异由代码补丁＋数据缩容＋负载类型三者混合构成"。

## 五、口径正确性

1. **`script_ms_per_s` 口径 —— 探针侧：正确且清晰。**
   `probes/measure-after-C1.mjs:80,83,102,111`：
   ```js
   const metricsBefore = await readMetrics();          // Performance.getMetrics
   await page.waitForTimeout(WINDOW_SEC * 1000);
   const mAfter = await readMetrics();
   const delta = (k) => Number((((mAfter[k] ?? 0) - (metricsBefore[k] ?? 0)) * 1000).toFixed(1)); // 秒→毫秒
   script_ms_per_s: Number((delta("ScriptDuration") / WINDOW_SEC).toFixed(1)),
   ```
   → **确为「窗口内 CDP `ScriptDuration` 增量（秒）×1000 ÷ 窗口秒数」**，即 **CDP 主线程脚本执行时长 ÷ 窗口秒数**。单位与量纲正确，与基线 `measure3.json` 的 `script_ms/20s` 口径**同源可比**。**✅ 确认。**

2. **探针的两处口径缺陷（影响可比性，文档未提）**：
   - `ws_rate_per_s`（:96）用 `wsTotal / ((performance.now()-c.started)/1000)` 计算，而 `wsTotal` 在**每个窗口开头被清零**（:76）、`c.started` 却是**装置安装时刻**（:40，早于窗口）→ **4 个窗口里只有第 1 个的分母接近 20s，第 2/3 个分母被拉长**，故 `ws_rate_per_s` **系统性偏低**（窗口越靠后偏得越多）。这是一处真实的**分母 bug**（第 3 个窗口尤其明显：`N734-active::dwell` 记 1.7 帧/s = 110 帧 / ~65s）。
   - `session_list` 抓取（:128–153）用裸 `fetch("/api/session.list", {body:"{}"})`，**缺 DSH RPC 信封**（应为 `{"type":"client-request","rpcId":...,"method":"session.list",...}`）→ 宿主返回 `bad-request / invalid client-request message`，**恒为 680 B、`items:null`**。我实测复现：HTTP 200、**680 B、items 恒 null**（`/tmp/accept-audit/v-audit.json::session_list`）。**因此探针从不测量 N，也从不报错**（`if (!res.ok) continue;` 只在非 2xx 才跳过）。**文档中所有"改后 N=734 / 2396"的表头都不是探针测出来的**（见 §一.3 L1c）。

3. **文档把口径写错/写含糊的地方**：
   - **错**：`BEFORE-AFTER.md:43` 「`session.list` 字节（**items**）」——实际是**整响应信封/整文件**（3,940,937 vs 3,941,050，开销 113 B）。同批 E1 证据明确分列"items / 信封"，此处标反。**口径张冠李戴。**
   - **含糊**：`BEFORE-AFTER.md:12` 表头「**基线**（未打补丁，N=2396）」——N 既错（2361/2386），"未打补丁"也只对 C1 成立（对 B1 服务端补丁不成立，抓取时补丁已在盘上）。
   - **含糊**：「可比条件」四字被用作**结论授权**，但未定义可比性判据（只看 ws？还看 N？看帧类型？），实际执行只看了 ws 一项。
