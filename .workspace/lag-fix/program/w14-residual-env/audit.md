## 0. 一句话裁决

> **① 是环境为主因，且已定量：在用户真实显示配置（5120×2880 背衬 @ DPR2）下，一个不含任何 DSH 代码的极简页做"整屏整幅重绘"时，帧时间从 17.04 ms 涨到 23.40 ms（中位，3/3 rep 复现），等效 **42.4 Hz**，帧时间 ×1.37、**掉帧 27.2%**；同一个页面、同一份主线程工作，在 1440×900@DPR1 下是 **60.0 Hz，0 掉帧**。**
> **② DSH 页面本身在"持续帧成本"上没有额外多付：H 档 B−C = −0.06 ms/帧、L 档 B−C = −0.10 ms/帧（即与空白页同级）。DSH 独有的表现是"偶发 ~1 秒长停顿"（H 档 3 次里 2 次出现 max ≈0.98–0.99 s），但它**未能与污染区分开 ⇒ 判 INCONCLUSIVE**。**
> **③ 放大器不是"帧缓冲面积"本身，而是 **DPR2 这条高 DPI 路径**：在**完全相同**的 14.746 Mpx 背衬、**完全相同**的 mutter 5120×2880→3840×2160 双线性降采样下，DPR1 是 17.06 ms（60 Hz 级），DPR2 是 22.47 ms（6 个窗口合并中位）⇒ **+5.41 ms/帧**（独立复算见 §12 校验）。**

## 2. 判据与仪器自证（BATCH-PLAN §五 第 19–20 条）

- **主判据（Gecko 可用通道）**：**页内 wall-clock rAF 间隔 + 窗口播种**。`runWindow()` 在同一个页内异步调用里完成：开记录 → 播种 6 帧（**保留块前那一帧**，不做"丢弃首帧"）→ 打 `loadStart` 边界 → 页内 `setTimeout` 保持窗口 → 打 `loadEnd` → 保留 4 帧尾部。时间戳一律取 rAF **回调入口**的 `performance.now()`。
- **❌ 未能执行主判据的另一半**：**Gecko 侧没有 CDP `RunTask`**（Firefox 155 已移除 CDP，`/json/version` 不再提供）。故 §五.19⑤ 里"主判据 = CDP `RunTask`（类别含 `disabled-by-default-devtools.timeline`）"在**本引擎上不可用**，本线显式改用该条指定的页内替代判据。**这一点必须随结论一起引用。**
- **❌ Gecko 无 LongTask / LoAF 通道**（§五.9：静默接受 `observe()` 却永不投递）。本线**全程未把"0 长任务/无长帧"当证据**，也未使用 LongTask 作任何立柱。
- **阳性对照（页内 `setTimeout` 注入，§五.13/19⑤）**：每窗注入 4×120 ms 忙等，**40/40 个窗口全部检出 4/4**（判据 = rAF 间隔 >100 ms 计 1 次）。⇒ 帧通道在**每一个**窗口都活着。
- **阴性对照**：空白静态页在 4 个档位（H / L / H1 / FULL2）共 **12 个窗口**，**p50 恒为 17.04 ms、max ≤17.44 ms、>33 ms 帧数恒为 0**。
- **时钟自证（§五.15）**：`privacy.reduceTimerPrecision=false`，页内读回 `performance.now()` 粒度 **0.02 ms**（默认 1 ms 的夹取已解除）。
- **DPR 自证（§五.10）**：每个窗口都读回 `devicePixelRatio / innerWidth / innerHeight / backingW / backingH`；背衬面积是对照表的自变量本身（见 §3），不是假设值。
- **`>50ms` 帧计数只作相对 KPI**（§五.19④：分辨下界 ≈40–50 ms）。A 档 @H 有 10–38 帧 >33 ms 却 **0 帧 >50 ms** —— 这正是该量化的体现，本线不把它当灵敏度判据。
- **可见性**：**未**使用 `visibilityState` 作为"帧在产出"的证据（§五.19⑤ 禁用）。所有窗口 `visibilityState=visible`，但 `document.hasFocus()=false`；帧确实在产出由"实测 rAF 速率 + 4/4 阳性对照"证明。

## 4. DPR 判别实验（同背衬面积，只换 DPR）——**本次最关键的对照**

`out/matrix-main-1790062090371.json`。两个档位的**背衬像素数完全相同（5120×2880 = 14.746 Mpx）**，mutter 的 5120×2880→3840×2160 降采样**也完全相同**；唯一自变量是应用 DPR（以及随之而来的 CSS 逻辑尺寸）。

| cond | DPR | CSS 视口 | 背衬 | A 逐 rep p50 | A 中位 | A eff Hz | C 逐 rep p50 |
|---|---|---|---|---|---|---|---|
| **H1** | **1** | 5120×2880 | 5120×2880 = 14.746 Mpx | **17.06 / 19.36 / 17.06** | **17.06 ms** | 53.7 / 47.6 / 54.0 | 17.04 / 17.04 / 17.04 |
| **H** | **2** | 2560×1440 | 5120×2880 = 14.746 Mpx | 22.20 / 21.52 / 19.82 | **21.52 ms** | 44.6 / 46.1 / 49.9 | 17.04 / 17.04 / 17.04 |
| **H（主矩阵）** | **2** | 2560×1440 | 5120×2880 = 14.746 Mpx | 23.40 / 25.34 / 22.74 | **23.40 ms** | 42.4 / 40.2 / 43.3 | 17.04 / 17.04 / 17.04 |

**DPR2 合并（6 个窗口）中位 = 22.47 ms；DPR1 合并（3 个窗口）中位 = 17.06 ms ⇒ Δ = +5.41 ms/帧。**
且在 DPR1 下，14.746 Mpx 的整屏整幅重绘 **17.06 ms ≈ 空白页 17.04 ms**（+0.02 ms）⇒ **DPR1 时这块 5120×2880 帧缓冲 + mutter 降采样本身是"免费"的**。

**推论（受 §8 边界约束）**：放大器是 **DPR2 的高 DPI 渲染/合成路径**，其代价随"应用自己的设备像素面积"增长；**不是** mutter 降采样本身，也**不是**单纯的大帧缓冲。

## 5. 无浏览器对照（Group D，`out/x11-env.json`）

方法：用 `xrefresh -geometry WxH+0+0` 从 Node 串行死循环强制 X 重绘，同时用 /proc 计 Xorg + gnome-shell（mutter）CPU。**不涉及任何浏览器、不改任何设置。**

| 面积 | Mpx | 重绘次数/秒（rep1 / rep2） | present CPU ms/次 | mutter 自身 % |
|---|---|---|---|---|
| 无重绘（阴性） | 0 | — | — | 3.75 / 7.50 |
| 全屏 5120×2880 | 14.746 | **251.5 / 161.7** | **1.233 / 1.793** | 7.25 / 7.75 |
| 半屏 2560×1440 | 3.686 | 292.9 / 273.4 | 0.913 / 1.316 | 11.49 / 12.49 |
| 小面积 640×480 | 0.307 | **326.5 / 327.7** | **0.835 / 0.786** | 11.00 / 10.25 |

- 全屏重绘相对小面积：**present CPU 每次 1.48–2.28×**、**可达速率降到 1/1.3–1/2.0**，而像素数是 **48×**。
- **mutter 自身 CPU 在全屏时反而更低**（单次全屏合成 < 多次小面积合成）。
- ⇒ 在 Xorg/mutter 侧，present 路径**只轻微随面积增长**，远非 48× 比例。这与第 3/4 节"掉帧时 mutter CPU 仍只有 4.5–7% 且不随动画上升"一致。

## 7. 显式写出"未能测到"的部分（边界）

1. **Gecko 无 LongTask / LoAF 通道**（§五.9）⇒ **没有任何主线程长任务归因**；本线只用 wall-clock rAF 间隔。凡"Gecko 上 0 长任务"的说法在本线一律不作为证据。
2. **Gecko 无 CDP**（Firefox 155 已移除）⇒ §五.19⑤ 的**主判据 `RunTask` 在本引擎不可用**；这是**引擎级边界**，不是本线省略步骤。
3. **`>50 ms` 不是灵敏度判据**（分辨下界 ≈40–50 ms）。A@H 大量 33–50 ms 帧在 `>50ms` 计数里**看不见**（10–38 帧 >33 ms、0 帧 >50 ms）⇒ 若只看 `>50ms` 会得出"环境没问题"的**假阴性**。
4. **无法打开 DSH 会话视图**：无深链（recipe 源码级确证：shell 与全部 client 插件里 `pushState/replaceState/location.hash|search|pathname` 命中 0）；`[role=tree]` 的 11 行是**工作区**行，其内层按钮打开的是 **Rename/Delete workspace 菜单**（危险）；展开行为非确定（同一坐标序列在 recon9 成功、recon10/驱动档失败）。⇒ **"长会话列表滚动"与"btw 打开"未被驱动，"长对话滚动"这个最接近用户真实场景的负载完全没有测到。**
5. **B 档负载不是用户真实主场景**：实际驱动的是「Sessions 树滚动 + 工作区展开/折叠 8–9 次 + 设置弹窗打开 + 切 4–5 个导航项 + 指针扫掠 409–479 次」，全部只读。这**不能替代**"滚动长对话"的成本。
6. **GPU 时间不可见**：掉帧时 `ff` 进程 CPU 仅 10–12%（单核 1/8），mutter 4.5–7%、Xorg 2.6–5.5% ⇒ **CPU 未饱和**；因此"瓶颈在 GPU/呈现路径"是**由排除法反推**，不是直接测量。Group D 也是 CPU 代理。
7. **有头 Chromium 起不来**（SIGTRAP/DLP）⇒ 无跨引擎同机对照；"Chrome 顺 / Firefox 卡"只能是用户证词，本线无法复现或否证。
8. **`visibilityState` 被显式排除在证据之外**（§五.19⑤）；所有窗口 `hasFocus=false`，窗口并未获得输入焦点（用真实 BiDi 指针输入绕过）。
9. **机器非独占**：loadavg 4.3–7.0，32 核；peer 线在跑（短窗批次见 `headless_shell`）。锁定批次内普查仍见用户自己的 2 个浏览器。所有结论都建立在**同 rep 相邻配对 + 轮转次序**上（BATCH-PLAN §18 允许），**不用跨窗绝对数**。
10. **A 档是我自建的"整屏整幅重绘"极简负载**（`background-position` 每帧全幅重绘）；题目指定的极简页是 A2（波纹+托盘）。两者都**不含 DSH 代码**。A3（200vw×200vh 超大合成层 transform）只在早期短窗试跑跑过 1 rep，**不作为主结论**。
11. **mutter 每帧时间/帧率不可读**；降采样是 DCN 硬缩放还是 shader pass **未测**。
12. **未验证任何干预的端到端效果**：第 9 节全部是**方案**，本线**没有执行任何系统变更**（未改 scale、未改 DPR、未动显示器、未动产品文件）。

## 8. 机制小结（区分"测得"与"推断"）

**测得**：
- 同机同页同工作，背衬 14.746 Mpx @DPR2 → 42.4 Hz；1.296 Mpx @DPR1 → 60.0 Hz（3/3 复现）。
- 同 14.746 Mpx 背衬、同 mutter 降采样下，DPR2 比 DPR1 **多 +5.41 ms/帧**；DPR1 时整屏整幅重绘 ≈ 空白页（+0.02 ms）。
- 掉帧窗口内 **ff CPU 10–12%、mutter 4.5–7%、Xorg 2.6–5.5%** —— 没有任何一方饱和。
- 无浏览器对照：全屏强制重绘的 present CPU 仅是小面积的 **1.5–2.3×**（像素数 48×）。

**推断（未直测，需引用时标注）**：
- 瓶颈位于 **GPU 侧的 DPR2 渲染/合成路径**（WebRender 在高 DPI 下的光栅+合成），因为 CPU 侧全面未饱和而 /proc 读不到 GPU。**"GPU 侧"是排除法结论。**
- mutter 的 5120×2880→3840×2160 双线性降采样**不是**主因（DPR1 同帧缓冲同降采样下免费）。

## 9. 最小干预方案（**只给方案，本线未执行任何系统变更**）

### I1（首选）：把显示器缩放从 150% 改回 100%
- **依据**：§4 —— 同 14.746 Mpx、同降采样下 DPR1 17.06 ms（≈60 Hz）vs DPR2 22.47 ms（≈43 Hz）。scale 100% 后 X 屏幕变 3840×2160、应用 DPR 变 1，落的正是这条被测过的自由路径。
- **预期改善**：**A 档整屏重绘 42.4 Hz → ≈60 Hz（回收 ~100% 的掉帧）**；按 +5.41 ms/帧 计，帧时间预计回到 17.0–17.1 ms。**注意**：3840×2160@DPR1 的像素数（8.29 Mpx）介于我测过的 14.746 Mpx@DPR1（免费）与 3.686 Mpx@DPR1（免费）之间，两点都免费 ⇒ 预期安全。
- **代价**：整个桌面变大、内容物理尺寸变小（这是用户偏好问题，不是技术问题）。
- **回滚**：设置 → 显示器 → 缩放改回 150%（等价于把 `~/.config/monitors.xml` 的 `<scale>1.5</scale>` 写回）；无需重启，改完立即生效。
- **可验证性**：改后用本线脚本复测 `--conds "H1:1:5120:2880"` 与 `--conds "FULL2:2:2560:1440"` 同 rep 配对，看 A 档 p50 是否回到 ≤17.2 ms。

### I2（不改桌面缩放）：降低"应用自己的设备像素面积"
- **依据**：DPR2 下 1.296 Mpx → 0 ms 代价；5.184 Mpx → 0…+3.4 ms（**分裂，INCONCLUSIVE**）；14.746 Mpx → +5.4…+8.3 ms。
- **做法**：不要把 Firefox/DSH 窗口最大化占满 5120×2880；把窗口控制在整个屏幕的 ~1/4 面积以内（≈1.3 Mpx 档，实测 0 代价）。
- **预期改善**：把 +5.4 ms/帧 降到 ≈0（在 1.296 Mpx 档已实测为 0）。**注意**：5.184 Mpx 档数据分裂，所以"1/4 屏幕"这个边界值我只能给到"1.296 Mpx 已确证为 0"。
- **回滚**：重新最大化窗口。

### I3（假设，未验证）：把显示器接到 RTX 4090
- **依据（间接）**：瓶颈判定在 GPU 侧且 CPU 全未饱和；内容进程自报渲染器是 **AMD Raphael（2 CU）**。换到 4090 有可能吸收这 +5.41 ms。
- **预期改善**：**未验证，不做幅度承诺**。上界估计 = DPR2 相对 DPR1 的差额 **+5.41 ms/帧**。
- **反证据（必须先读）**：§5 显示 present/降采样路径本身代价很小（1.5–2.3×，非 48×），且 DPR1 同路径免费 ⇒ 若瓶颈确实只在"高 DPI 光栅"上，换卡收益应当明显；但本线**没有**任何跨 GPU 数据。
- **回滚**：线接回核显输出。

### ❌ 不建议的方向（有反证据）
- **"mutter 的 5120→3840 降采样是主因"** ⇒ 被 §4 否证（DPR1 同帧缓冲同降采样下免费）。
- **"机器任何动画都卡"这种均匀税** ⇒ 被 §3 否证：空白页与 1.296 Mpx 档的所有组都是 60 Hz。
- **"Chrome/a11y"这条解释线** ⇒ 本线未采用（用户已拒绝；Firefox AT-SPI 已确认关闭），且 Firefox 侧掉帧与 a11y 无关地出现在**无 DSH 代码的极简页**上。
