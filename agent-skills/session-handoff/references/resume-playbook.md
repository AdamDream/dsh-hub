# 接手模式操作手册（`resume-playbook`）

拿到一份 `<前缀>_NEXT_SESSION_PROMPT.md` 之后的固定动作。**格式细节以 `handoff-spec.md` 为准**，
命令以 `generate-playbook.md` 为准；本文件只写**顺序、判据与停手条件**。

## 接手六步

1. **加载本 skill 的接手模式**：阅读本文档；确认交接件路径与 `repo_root`（交接件头部 YAML）。
2. **实跑核对（先核对，后相信）**：按 `§0` / `§1` 逐条实跑——`git rev-parse HEAD` 与头部 `git_head` 比对、分支比对、关键文件是否存在（用 `generate-playbook.md` 的 `probe-reachability.sh` 对交接件跑一遍可达性）、`§1` 的已核实项抽 3 条复核。**任何一条对不上都先记下来，不要先动手**。
3. **读勘误块并回报偏差**：读头部 YAML 之后的勘误回写块，逐条对照**刚才实跑的现状**，指出哪些勘误仍然成立、哪些已经被后续工作推翻。**本步只读、只回报，不改文档**（回写在第六步）。
4. **复述理解 + 前 3 个动作**：按「复述模板」输出，明确说出你理解的当前状态、`§2` 的前 3 个动作（对应 P0–P2）、以及你发现的歧义。
5. **检查 `§2` 前置条件闸门**：逐条对照「前置条件闸门」表；**不满足即停**，把不满足项与需要谁裁决写清楚，等用户回复。
6. **用户确认后才动手**；动手过程中若发现与交接文档不一致的偏差，**回写勘误块**（时机与要素见「勘误回写规则」）。

## 前置条件闸门

`§2` 的每个任务都带前置条件；逐条判：

| 闸门 | 满足条件 | 不满足时的动作 |
|---|---|---|
| 事实基线一致 | `git_head` / `git_branch` 与 `§1` 一致（或偏差已解释） | **停**：报出偏差，问用户以现状还是以文档为准 |
| 依赖文件/产物到位 | `§8` 索引里该任务依赖的路径全部可达 | **停**：报出缺失路径与缺口，问是否先补前置 |
| 前置任务已完成 | `§2` 里标为该任务前置的项已完成（有 commit 或产物指向） | **停**：改从前置任务开工，并回报调整 |
| 用户裁决已给 | 该任务没有落在 `§5`「需你裁决」清单里 | **停**：把待裁决项提给用户，不自行决定 |
| 不在「不得重开」范围 | 任务不触碰 `§4` 已裁决不得重开的事项 | **停**：指出冲突，请用户明确推翻或改派 |

**闸门不满足时一律停并问，不许「先做着看」。**

## 复述模板

接手后第一次回复用这个骨架（五项**逐项写全**，不许省略）：

```text
1. repo_root：<实跑得到的仓库根>（交接件记的是 <头部 YAML 的 repo_root>）
2. git_head：<实跑 HEAD>；与 §1 记的 <头部 git_head> —— 一致 / 不一致（不一致则写差在哪里）
3. 前 3 个动作：①<对应 §2 P0> ②<对应 P1> ③<对应 P2>（含每项的可判定标准）
4. 歧义：<逐条列出发现的不一致或不清楚处>；未发现歧义则显式写「未发现歧义」
5. 闸门判定：<逐条给「通过」或「停并问 <原因>」>
```

- 第 4 项**必须显式表态**：要么列出 ≥1 条歧义，要么明确写「未发现歧义」；留空视为未完成复述。
- 第 5 项必须落地到「通过」或「停并问」，不允许写「大致可以」。

## 勘误回写规则

- **回写时机**：第六步动手之后，**凡实测与交接文档不一致**（HEAD 变了、文件被删/移、坑已不成立、裁决被推翻）即回写；或在动手前发现文档已明显过期也可先回写一条。
- **每条要素**：日期 + 证据（实测命令输出或文件路径）+ 修正内容 + 被修正的原小节编号。
- **可累积**：新条目追加在后面，**原文不删不改**。
- **格式**（字段、位置、写法）以 `handoff-spec.md`「勘误回写块（不编号）」为准，本文件不重述格式。

## 禁止事项

1. **不得跳过第二、三步的实跑核对**直接开工。
2. **不得在闸门不满足时开工**，也不得把「停并问」简化成「边做边问」。
3. **不得重开 `§4`「已裁决不得重开」的事项**；要推翻必须由用户明确指示。
4. **不得把 `[仅记忆]` 标记的内容当作事实**（尤其不得据此修改代码或结论）。
5. **不得编辑 `docs/program-notebook.md`**——那只在交接文档里作为「建议下个会话更新的条目」出现。
